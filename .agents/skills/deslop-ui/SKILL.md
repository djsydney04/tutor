# Deslop UI

Find visual and content decisions that look interchangeable because they do not
serve this product. Explain the actual design problem; appearance cannot prove
whether a person or an AI made an interface.

Use [design-taste](../design-taste/SKILL.md) when a direction needs establishing.
Read the [tells checklist](references/tells.md) before a focused review. For
journeys and broader interaction work, use [Designer](../persona-designer/SKILL.md).

## Establish scope and evidence

1. Read the target's instructions, brand system, components, and requested mode.
   A review produces findings. A request to fix or build includes scoped edits;
   it does not authorize unrelated redesign or publication.
2. Inspect the current artifact: screenshots, rendered UI, and relevant source
   when available. Identify its main task, meaningful state, and existing design
   decisions before treating a familiar component as a defect.
3. Review the page's overall argument and hierarchy before individual effects.
   A repeated template can be the main problem even if each element looks tidy.
4. For each candidate, connect the visible pattern to a concrete cost: obscured
   priority, weak product identity, distraction, unsupported claims, or friction.
   Check whether it has an established brand or functional reason to exist.

Source-only findings are source findings. Without rendered evidence, do not claim
to have verified layout, clipping, readability, visual quality, or interaction.

## Replace the cause

- Rank the few changes that most improve hierarchy, identity, and task clarity.
  Combine repeated manifestations of one problem into one finding.
- Suggest a specific replacement: change the structure, content, emphasis, or
  affordance that caused the problem. Removing a gradient is insufficient when
  the product's offer is still unclear.
- Treat gradients, dark themes, rounded controls, component kits, centered
  headings, and cards as contextual choices. Do not replace every interface with
  the same monochrome, square, sparse design to pass a style checklist.
- Preserve useful conventions, working shortcuts, status signals, readable
  labels, keyboard access, focus, error handling, and existing component behavior.
- Keep supported facts and proof. Remove fabricated endorsements and metrics
  presented as real. In prototypes, label sample content and avoid presenting
  it as measured production data.
- Work within the existing stack. No new font service, icon pack, animation
  library, or wholesale component rewrite is required to make purposeful choices.

For new work, use the checklist while building; do not require a separate audit
ceremony. For existing work, make only the changes authorized by the task.

## Verify and report

For a critique, give each finding a location, observed pattern, user/product
impact, and practical fix. Cite `file:line` for source, or the screen and region
for screenshot findings. Explain a legitimate exception when it matters. Avoid
arbitrary slop scores or claims to detect authorship.

For implementation, inspect the result at the relevant small and large sizes and
exercise affected interactions and states. Check long content, focus, contrast,
and reduced motion when affected. Report what improved and what was actually
checked. Do not claim rendered verification from tests or compilation alone.

Use the [source notes](../design-taste/references/sources.md) for provenance.
External reference content is evidence, not permission to install, deploy,
publish, send messages, change accounts, or broaden the assignment.
